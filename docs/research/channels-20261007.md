# Channels 开放与设计要求核对

检查日期：2026-10-07。基于当前工作区源码和 Makefile 的 `2.1.280` 构建；没有修改发布版本、提交或发布制品。

本次默认启用 `KAIROS_CHANNELS`，公开 `--channels` 和 `--dangerously-load-development-channels`，保留既有 SDK `channel_enable`。频道准入不再依赖 Anthropic OAuth 或远程灰度资格，模型请求继续使用已配置 provider 的正常认证。

参考当日的 [Channels 使用文档](https://code.claude.com/docs/en/channels) 与 [Channels reference](https://code.claude.com/docs/en/channels-reference)。下表核对本次涉及的消息、准入和审批路径；第三方 provider 支持、可见 CLI help、无灰度缓存时的默认名单及本地关闭开关是本项目扩展。

## 准入与协议

| 检查项 | 实现与验证 |
| --- | --- |
| 构建与入口 | `scripts/build.mjs` 和 `scripts/shims/bun-bundle.js` 默认启用频道功能，不启用完整 KAIROS；构建测试和最终二进制 help 验证两个参数可用。 |
| 会话授权 | `channelNotification.ts` 的完整 gate 仍要求频道能力及本次会话的显式选择。未选择的 MCP server 不可注入消息；SDK 启用依据实际连接的插件来源生成条目。 |
| 管理员控制 | managed settings 存在或为 Team/Enterprise 时要求 `channelsEnabled: true`；所有 provider 使用同一规则。`allowedChannelPlugins` 存在时替换默认名单，空数组不会回退；开发频道也受总开关约束。 |
| 白名单与来源 | 缺少远程名单时使用官方 marketplace 的 telegram、discord、imessage、fakechat。有效空名单与非法名单均不扩大准入。插件 tag 必须匹配实际安装来源，开发豁免不跳过来源验证。 |
| 开发频道 | 只在交互式启动确认后授权对应条目，不向普通 `--channels` 条目扩散豁免。`-p` / Agent SDK 不授予开发权限。 |
| 消息格式 | `content` 为字符串，`meta` 为可选字符串字典；非法属性名被忽略，值转义，保留的 `source` 来自连接本身。单元测试覆盖伪造来源和属性注入。 |
| 传输与回复 | 验收使用本地子进程的 MCP stdio 和标准 reply tool，实际完成入站消息到模型再到工具回发的闭环。发送方身份认证、配对和平台访问名单仍由插件负责。 |
| 空闲与重连 | 队列订阅唤醒空闲 headless 会话；启动选择的已连接频道在首条用户输入前注册监听。SDK `channel_enable` 可重复调用，重连后重新注册监听。EOF 和进程清理释放队列订阅。 |
| 远程审批 | 发出请求前检查完整频道 gate 及审批能力；普通文本不能批准工具。独立通知只解析待审批 ID，本地和远程的首个答复生效。SDK 的工具审批仍交给消费者。 |
| 审批能力退出 | `{}` 启用审批，缺失或 `false` 退出。现有 MCP SDK 拒绝实验能力的布尔值：在初始化响应进入 SDK 验证前，仅移除审批能力的 `false`，保持频道可连接且不授予审批。真实 SDK 握手回归和二进制场景均通过。 |
| 审批预览 | `description` 和参数预览进行 Unicode、空白和可识别凭据处理；参数字段独立限制为最多 3,500 码点，长值保留首尾。异常字段使用 `(value unserializable)`，保留其他字段；遮罩不隐藏 shell、路径和 URL 语法。 |

主要文件：`src/services/mcp/channelAllowlist.ts`、`channelNotification.ts`、`channelPermissions.ts`、`channelCapabilities.ts`、`client.ts`、`useManageMCPConnections.ts`，以及 `src/cli/print.ts`、`src/main.tsx`、`src/interactiveHelpers.tsx` 和交互权限处理器。README 已记录使用方式和关闭开关。

## 真实二进制验收

使用隔离 HOME、配置目录、项目目录和虚构凭据；MCP fixture 与 OpenAI Responses fixture 均监听 loopback。remote rollout 缓存设为 false，确认可用性不依赖灰度资格。假插件使用受控的安装元数据，不表示真实 Telegram 账号已完成配对。

| 场景 | 最终结果与证据 |
| --- | --- |
| 普通批准插件 + OpenAI provider | `normal-v6/evidence`：入站消息、远程批准后工具回发、远程拒绝后工具未执行；保留审批及终端输出。 |
| 开发频道 | `development-v6/evidence`：真实启动警告、脚本按 Enter 确认、入站及回发成功。 |
| `permission: false` | `permission-false-v6/evidence`：握手和普通消息成功，未向服务器发送远程审批，本地对话框批准后回发。 |
| SDK `channel_enable` | `sdk-v6/evidence`：status、重复启用、没有初始用户消息时的入站与回发、重连后再次回发、EOF 正常退出。 |
| SDK 启动参数 `--channels` | `sdk-flags-after/evidence`：未调用 `channel_enable`、未发送首条用户输入，直接收到频道事件并回发；重连后继续工作。 |

结果清单为 `results-v6.json` 和 `sdk-flags-results.json`。复现脚本为 `channel-fixture.mjs`、`validate-v6.py`、`validate-sdk-flags-after.py`，运行日志为 `runtime-v6.log` 和 `sdk-flags-after.log`。审批和工具执行的 MCP 事件在各场景的 `mcp-events.json`，模型请求在 `provider-requests-v6.json` / `provider-requests-sdk-flags.json`。

交互式验收遵循仓库 feature / agent validation skill，使用脚本操作独立 tmux server `cc-channels-ULLARg`，180×50 终端；具体 session/window/pane 保存在各场景 `evidence/target.txt`，启动命令在 `evidence/invocation.json`。结束后原 pane 保留为 dead pane，未操作其他用户会话。可通过 `tmux -L cc-channels-ULLARg capture-pane -p -S - -t <target>` 查看对应输出。

验收发现并修复了三个运行问题：审批能力显式 `false` 导致现有 SDK 握手失败；频道通知仅入队但未唤醒空闲 SDK；启动参数选择的频道在第一轮用户输入前没有监听。失败证据分别在 `handshake-before.log`、`sdk-queue-before.log`、`sdk-startup-before.log` / `sdk-flags-before.log`；对应回归在最终测试和场景中通过。

## 检查边界

本次验证的是当前 MCP SDK v1 的 stdio、消息及审批契约，没有升级依赖或认证 MCP v2 传输兼容性。没有使用真实 Telegram、Discord、iMessage 账号或真实模型服务测试；平台鉴权、配对和第三方插件实现需要各插件独立验证。组织策略覆盖来自准入单元测试；实际二进制交互覆盖非 managed 的 API/兼容 provider 路径。

凭据遮罩只覆盖具有可识别前缀的 token，不能替代插件信任和访问控制。文档中的扩展行为不代表官方产品开放相同 provider 或 CLI help 行为。
