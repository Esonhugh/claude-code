# 官方 Code Mode 2.1.325 的工具调用与执行机制

2026-11-15 核对。npm 上 `@anthropic-ai/claude-code` 最新为 2.1.325，仓库根目录的 `./official-claude` 是 2.1.322。本文只读分析两个版本的 darwin-arm64 原件，没有运行解包出的 JavaScript，也没有改动源码。

结论：官方把 Code Mode 做成了独立的一套。模型只看到 `REPL`（以及 `Poll`、`StructuredOutput`），在 `REPL` 里写 JavaScript 调用其他工具。脚本里的每次工具调用仍然逐项经过 schema 校验、`validateInput`、PreToolUse hook、权限判定、`tool.call` 和 PostToolUse hook，但这条流程是 `EvalTool` 模块里自己写的一份，没有调用主循环的执行函数。脚本在 CLI 进程内的 `node:vm` context 里运行，隔离到 realm 一级，不是 OS 沙箱。

本仓库只有 `src/tools/REPLTool/constants.ts` 和 `primitiveTools.ts`。`src/tools.ts:19` 在 `isAnt()` 时 require 的 `REPLTool.js` 不存在，所以本地没有对应的执行逻辑。`src/services/tools/toolHooks.ts:825` 的 `resolveHookPermissionDecision` 注释写明它由主循环和 `REPLTool/toolWrappers.ts` 共用，这是 2.1.88 恢复源码里留下的共享点。

## 启用条件

开关是环境变量 `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1`，显示名 `Code Mode (experimental)`。`chunk-ev5tx9th.js:46-67` 按 flagSettings、userSettings、shell 的顺序读取，任一处写 off 都得到 `not_asked`。

启动时由 `settleCodeModeOptInAtStartup`（`chunk-vpz3nf29.js`）调用 `yKa`（`chunk-ev5tx9th.js:178`）。本地检查 `F()`（:161-177）依次是：

- 必须是官方 standalone 构建（runtime）；
- 有 Bash；
- 入口是交互 CLI，不是后台会话、teammate 或 Remote Control；
- `--tools`、`--disallowedTools` 或 deny 规则没有去掉 REPL；
- engine check 没有挡住；
- provider 是 firstParty，不用 apiKeyHelper 或 AUTH_TOKEN；
- 不在 HIPAA/ZDR 合规模式，不开 OTel；
- 模型合格；
- 没有装带 JS hook、会检查 tool call 的 mod。

远端还要过 GrowthBook gate `tengu_rustling_blossom`（:86-93），`~/.claude.json` 里 `codeModeCaveatsAcceptedV1` 与 `codeModeAutoModeCaveatAcceptedV1` 要为 true（:109-112）。用户在 `CodeModeOptIn` 对话框（`chunk-1f850fa5.js:581-726`）同意后，进程带着 `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE_RESTART` 和 `..._RESTARTED_FROM` 重启（`chunk-ev5tx9th.js:241-248`）。对话框原文提醒 auto mode 的分类器 "reads each piece of JavaScript once, before it runs. It doesn't check each tool call"。

运行时判定在 `chunk-xjqp3eha.js`：

- `le()` 是 opt-in 已接受。
- `na()`（:557）还要求 `se()` 为真，且 engine check 没有挡住（`kjs`，:584）。
- `se()`（:567）排除远端 workspace 的 thin client，并要求 `!OVn()`。`OVn`（:678）在 sandbox 提供 `commandNetworkListsOffered` 时让 Code Mode 让位。
- `pinCodeMode`（`Ojs`，:684）只能 pin 成 off。

## 模型看到的工具和 prompt

`hideCodeModeOnlyTools`（`sZ`，`chunk-xjqp3eha.js:741-751`）在 Code Mode 生效时删掉全部 MCP 工具，以及 `REPL`、`Poll`、`StructuredOutput` 以外的工具。API 请求体直接用 `tools: sZ(...)`（`chunk-wqb2b4v0.js`）。模型如果仍然调用了被隐藏的工具，会收到 "`X is only available inside REPL. Use REPL with code: await X({...})`"。

两组常量（`chunk-xjqp3eha.js:768-769`）：

- `CODE_MODE_ONLY_TOOLS`：Read、Glob、Grep、Bash、PowerShell、NotebookEdit。Code Mode 开启时从工具池整组移出（`chunk-6fgj334j.js`）。
- `REPL_PRIMITIVE_TOOL_NAMES`：上面一组再加 Write、Edit。Write、Edit 留在工具池，但不发给 API。

REPL 的 prompt（`chunk-g61t94xb.js:1549-1618`）开头是 "Your two tools are `REPL` and `Poll`; there are no other tools"。prompt 告诉模型：上下文持久、支持顶层 await、没有 import/require/process；每次 REPL 调用都是一次完整的模型往返，应当用 `Promise.all` 一次做完；输出包在 `<repl-output>` 里，每段截到 30000 字符。

prompt 里的 TypeScript 声明由 `pr()`/`Qo()`（:1362-1386）生成，每个工具一个全局 async 函数，另有 `tools.<name>`、`tools.list()`、`describeTool(name)` 和 `searchTools`。MCP 工具、`skill__*`、`ToolSearch` 和 REPL 自己不写进声明，只列 MCP server 名，由 `searchTools` 查找。

其他 prompt 段落也会改写：memory 段把 "with the Write tool" 换成 `write(path, content)`（`O0o`）；Chrome 段换成 "Code Mode 下 Chrome 和 computer use 不可用" 的说明（`xVn`、`Fde`）。

REPL 工具定义（:6704-6770）：`isEnabled` 等于 `na()`，`isConcurrencySafe` 返回 false，`toAutoClassifierInput` 返回整段 `code`。REPL 自身的 `checkPermissions` 在 auto 模式下交给分类器，其他模式直接 allow，权限判定落在脚本内的每一次工具调用上。

## 脚本内的工具调用

`Di()`（`chunk-g61t94xb.js:2962-2977`）为每个可调用工具生成一个 wrapper，同时用真实名和脚本安全别名登记。`Xi()`（:4679-4698）把 wrapper 挂到 vm 的 `globalThis`。每次调用先过 `Jr()`（上限和停止检查），再进 `toolWrappers[name](input)`；没有 wrapper 时抛出 `${name} is not available in this REPL call`。

可调用集合由 `On()`（:1259-1268）计算：会话工具去掉 REPL，再补上 primitive 工具。primitive 来自 `Kwe()`（`chunk-wqb2b4v0.js`），共 8 个，经过 deny 规则、MCP `effectiveMaxPermission==="blocked"`、`--tools` 列表和 `primitiveToolGrant` 过滤；平台没有对应 shell 时去掉 Bash 或 PowerShell（:1256）。`Ji()` 再用 `!mt(n, Co)` 去掉 REPL 一次（:5469），所以脚本不能递归调用 REPL。MCP 工具仍在会话工具列表里，只是对 API 隐藏，因此脚本可以调用它们（推断，依据是过滤代码）。

单次调用由 `Fi()`（:3187-3830）处理，顺序是：

1. `inputSchema.safeParse`（:3403）。MCP 调用带了 schema 没声明的参数时拒绝（:3406-3416）。async lane 里拒绝 `run_in_background`（:3418）。
2. 加载、隔离、路由检查（`yTs`、`Ebo`、`Rbo`、`PDr(Gmo(...))`）。路由结果为 `elsewhere` 时通过 `hosts.runInnerCall({..., canUseTool})` 交给远端主机（:3488-3530）。
3. 授权步骤（:3032-3159）：`validateInput`（:3043）→ PreToolUse hook `oon(...)`（:3058，可改入参或以 "Blocked by PreToolUse hook" 拦截）→ `ron(..., {replScriptCall: true}, canUseTool, ...)`（:3089）。`ron` 和顶层调用走同一条权限与确认路径。拒绝时返回 `Permission denied for ${name}: …`。
4. 执行 `tool.call(input, {...ctx, innerCall: true, toolUseId, innerCallHostToolUseId, fileReadingLimits: {maxTokens: Infinity, maxSizeBytes: 268435456}}, canUseTool, ..., {globLimits: {maxResults: 25000}})`（:3678-3721）。
5. PostToolUse hook `z_t(...)`（:3757），可用通过 `outputSchema` 的 `updatedToolOutput` 替换结果。抛错时运行失败 hook `non(...)`（:3803）。

装了 mods 的 `tool.call` hook 时，`Ei()` → `Oi()`（:3540-3610）会带 `isHookedRun: true` 重新进入 `Fi`。

与顶层调用不同的地方：

- 并发由 `callSlots` 控制，上限是 `min(CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY ?? 10, 10)`（:3172）。被调工具的 `isConcurrencySafe` 不参与判断（推断，依据是 grep 只找到 REPL 自己的定义）。
- 中止：每次调用建一个子 controller，挂在当前 turn 的 controller 上（:3012），每一步都检查 signal。
- 错误：内置工具 resolve 成 `{error}`（`Wd()`，:2926），MCP 工具抛 `McpToolError`，`detail` 里是解析后的 JSON（:1270、:1293-1296）。
- 结果以 JS 值交回脚本。MCP 的 text block 拼接后按 JSON 解析（:3342-3375）。Bash/PowerShell 落盘的大输出由 `or()`/`sr()` 读回（:3747-3790）。
- transcript：进度事件类型是 `repl_tool_call`，阶段为 `start`、`executing`、`complete`、`error`（:3317、:3378、:3810）。`va()`（:6058-6094）把每次完成的调用写成一对虚拟消息：`tool_use`（`isVirtual: true`，id 前缀 `repl_`）和 `tool_result`；`tool_result` 的 `content` 为空串或错误文本，真实结果放在 `toolUseResult`，并附带 `permissionDecision` 和 `sandboxViolations`。这些消息在 :7442 加入 `newMessages`。

脚本里另有 `file`/`write`/`edit` helper（:4882-4917），经同一个 `g` 路径调用 Read、Write、Edit；Write 因文件未读失败时，helper 会先读再重试。`spawnContext`、`releaseContext`、`contexts.X.log` 分别调用 Agent、停止任务和发消息的工具；它们只在 `!qc()` 时安装（:5021），而 `qc()` 等于 opt-in 已接受，所以 Code Mode 开启时看起来不会出现（推断）。

## 脚本的执行

脚本在 CLI 进程内运行，没有 worker，也没有子进程。

1. `new Bun.Transpiler({loader: "js", replMode: true})`（`chunk-g61t94xb.js:5537-5545`）转译源码，提供顶层 await 和最后一个表达式的值。`scanImports` 发现 import、动态 import 或 `require` 时报错 "Module loading (...) is not available in REPL — the vm context is sealed"（:5684-5698）。
2. 插入步数探针 `__replStep()`（:2334-2336）。`Function.prototype.toString` 被替换，打印函数时去掉探针（:5191-5228）。
3. `new vm.Script(code, {filename: "repl-tool-code.js", importModuleDynamically: sealers.rejectImport})`（:5849），然后 `runInContext(ctx, {timeout})`（:5389-5393）。

context 由 `vm.createContext` 加修补创建（`SY`，`chunk-av8gd5nc.js:130`），参数是 `codeGeneration: {strings: false, wasm: false}`（`chunk-g61t94xb.js:5054`），所以 `eval`、`new Function(string)` 和 WebAssembly 都不可用。context 里没有 `process`、`require`、`Buffer`、`fetch`。`Xi`/`lu`（:4648-4877）注入的全局只有：`console`（写进内存 ring buffer）、`log`、`self`、各工具 wrapper、`searchTools`、`describeTool`、`tools`、宿主实现的 timer、`atob`/`btoa`、`$`（shell）、`preview` 和子 context 相关函数。文件、网络和 shell 只能经由工具 wrapper 访问。

加固措施：

- `hardenVMIntrinsics`（`chunk-av8gd5nc.js:156`，列表在 :50-124）冻结 Promise、Object、Array、Function、async/generator 构造器、JSON、Math、Reflect、Proxy、Intl。
- sealers（`chunk-g61t94xb.js:4014-4646`）在用户代码运行前捕获内置对象；跨边界的 Error、ArrayBuffer、DataView 按自有数据属性重建；宿主函数用 `sealFn` 包装，`isSealedAsync` 确认全局上的工具函数仍是宿主原件（:4782）；`Promise.prototype.toString` 调用即抛错（:5056-5063）。

这是一层 realm 边界，防的是宿主对象泄露和原型篡改。它和 CLI 同进程，安全边界仍在工具的权限路径上（推断）。

### 状态

每个 agent 一个 vm context，key 是 `agentId ?? "main"`（:6984），保存在 `ReplSessions`（`chunk-gcw6cvys.js:39`），只在内存里。变量在多次 REPL 调用之间保留；重启、resume、fork、wake 之后不保留，prompt 里写明了这一点（:1601）。compaction 后会建新 context，并提示 "This REPL context is new … even those a compaction summary lists as still defined"（`chunk-xjqp3eha.js:535`）。一个 context 最多同时挂 8 个未结束的 eval（`chunk-gcw6cvys.js:10`、:53）。

### 后台执行与中止

async lane 只在 `auto` 和 `bypassPermissions` 模式下启用（`oZ`，`chunk-xjqp3eha.js:735`）。脚本 30 s 后还没结束就转入后台，先返回 `(dispatched #N)`（:6589），之后继续运行，和后来的脚本共享变量（:1663）。后台输出以 `<event kind="repl-eval">` 出现在 `Poll` 的结果里，`Poll` 的输入为空（`chunk-pg2sb68f.js`）。后台脚本的错误由 `chunk-qbfszyx1.js` 写成一对虚拟的 `REPL` tool_use/tool_result；`chunk-vt245mgz.js` 先压住内层工具的进度，等 REPL 回执到达后再发给 SDK 客户端。

按 Esc 调用 `interrupt()`（`chunk-gcw6cvys.js:440-455`），中止所有 controller、丢弃后续输出、清掉 timer。被取消的脚本再调用工具时拿到一个永不 settle 的 promise（:5404-5420），脚本停在那里，不会看到报错。停止后代码的 rejection 被吞掉，不会让进程退出（:5277-5285）。

### Engine check

`chunk-2hbz1qvr.js` 在关闭代码生成的 context 里验证几条 JSC 行为：不可配置的全局不能被重定义；在返回的 `globalThis` 上定义 class field 会抛错；对全局 receiver 调 `preventExtensions` 后不能再定义新属性。抛出的必须是 context 自己的 `TypeError`，thenable 的 `resolve` 必须属于 context 的 `Function.prototype`。结果取值为 `passed`、`both`、`thenable_after_await`、`rejected_definitions` 或 `threw_*`。

只有 `!Mp()`（不是 standalone 可执行文件）时失败才会关掉 Code Mode：`return e !== "passed" && !Mp()`。官方二进制里失败只记一条日志 "REPL mode's engine check failed … still allowed"（`chunk-xjqp3eha.js:580`）。从源码运行时会提示 "Run Claude Code with the repository's pinned Bun … or use a staff build"（`chunk-g61t94xb.js:5043-5046`）。

## 2.1.325 与 2.1.322 的差异

- 开关相关模块导出的名字完全一致，`H`、`F`、`q` 和 `chunk-xjqp3eha.js` 的开关函数逐段对比也一致。2.1.322 里这些代码在一个约 72 KB 的 chunk 中（`chunk-wyaw0eh8` / `chunk-ng449kwj`），2.1.325 拆成了约 21 KB 的 `chunk-xjqp3eha.js` 和几个小 chunk（拆分属推断）。
- 模型条件放宽：2.1.322 只接受 `claude-opus-5-5` 与 `claude-sonnet-5-5` 的精确 ID。2.1.325 的 `mPn`（`chunk-ev5tx9th.js:68-73`）改为版本号不低于 5.5，fable 和 mythos 系列不低于 5.2。文案从 "only works with Opus 5.5 and Sonnet 5.5" 改成 "…Opus 5.5, Sonnet 5.5 and later models"。
- `EvalTool` 新增 `dialogAnswer`：hook feedback 里的对话框回答以 meta 消息注入。新增提示 "This was checked from the session's folder, because the folder the command would run in may be on another host…"。
- 其余字符串差异是 minifier 改名或 chunk 拆分。

## 对本仓库的影响

本地要实现 Code Mode，需要补的部分：

- 内层调用的执行流程。权限部分可以沿用 `resolveHookPermissionDecision`，校验、hook、`tool.call`、虚拟消息写入要按上文的顺序补齐。
- vm 执行器：转译、步数探针、context 加固、sealers、engine check。

## 未核实

- 官方主循环（顶层 tool call）是否和 `Fi()` 共用了更多函数，例如 `ron`、`oon`、`z_t` 是否就是主循环用的那几个。本文只确认 `Fi()` 调用了它们，没有对照主循环的执行模块。
- 被调工具的 `isConcurrencySafe` 不起作用、MCP 工具可在脚本内调用、Code Mode 下没有 agent/team helper，这三条都只来自静态阅读，没有运行验证。
- 没有用真实账号启用 Code Mode 运行。GrowthBook gate 在官方服务端的取值未知。

## 复现

```sh
mkdir -p /tmp/cm && cd /tmp/cm
bunx npm pack @anthropic-ai/claude-code-darwin-arm64@2.1.325
mkdir -p x && tar -xzf anthropic-ai-claude-code-darwin-arm64-2.1.325.tgz -C x --strip-components=1
python3 bunx.py x/claude m325
```

`bunx.py` 按 Bun standalone 格式读取：文件末尾是 `\n---- Bun! ----\n`，前面 32 字节的 Offsets 依次为 `byte_count: u64` 和 modules 的 `{offset: u32, length: u32}`；module 表每条 52 字节，开头是 name 和 contents 两个 `{offset, length}`，都相对 `trailer - 32 - byte_count`。

```python
import os, struct, sys
data = open(sys.argv[1], 'rb').read()
end = data.rfind(b'\n---- Bun! ----\n')
byte_count = struct.unpack_from('<Q', data, end - 32)[0]
mod_off, mod_len = struct.unpack_from('<II', data, end - 24)
blob = data[end - 32 - byte_count:end - 32]
os.makedirs(sys.argv[2], exist_ok=True)
for i in range(mod_len // 52):
    no, nl, co, cl = struct.unpack_from('<IIII', blob, mod_off + i * 52)
    name = blob[no:no + nl].decode().split('/root/')[-1].replace('/', '_')
    open(os.path.join(sys.argv[2], name), 'wb').write(blob[co:co + cl])
```
